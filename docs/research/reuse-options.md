# CYD SD → Bluetooth source: reuse options

Research date: **2026-10-23**. Target reported as `ESP-32-2432SO28`, provisionally the original ESP32-2432S028 CYD family, **without PSRAM**; display/touch revision remains unconfirmed. Mandatory input: **AAC-LC, 44,100 Hz, stereo**. Mandatory selectable outputs: **AirPods Pro 2 over Bluetooth** and **external DAC line/headphone output over I2S**; simultaneous output is not required. MP3 playback alone does not satisfy this requirement.

Evidence labels: **D** = upstream documentation or inspected source; **I** = engineering inference; **U** = untested here. All linked sources are upstream author/vendor sources, accessed on the research date. No firmware was built, installed or flashed, and no target hardware was measured.

## Decision

**Evaluate Garionhk/CYD-MP3-Player first as the complete application shell, conditional on an AAC feasibility gate.** It already addresses this CYD's display, SD, pairing, transport and memory constraints. Its existing audio engine is MP3-specific: adopting it does **not** establish AAC support. The first milestone must play the required AAC file from SD through a decoder into 16-bit stereo PCM and `BluetoothA2DPSource`, with Wi-Fi and elaborate graphics disabled. [Project](https://github.com/Garionhk/CYD-MP3-Player), [inspected engine](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/app/audio.cpp).

**Preferred AAC experiment:** LC-only `AACDecoderHelix` → bounded PCM ring → ESP32-A2DP source, then integrate into that shell. **Fallback:** AudioTools + Helix + SdFat + A2DP, using the current upstream SD sender example and an AAC decoder; this has a simpler documented composition but requires building the product UI. **Second fallback:** ESP-IDF with Espressif's `esp_audio_codec` AAC/simple decoder and native A2DP source. None is a proven complete no-PSRAM AAC CYD player on the evidence inspected. Memory fit is **plausible, not established**; do not promise Fonix feature parity or simultaneous Wi-Fi.

## Fonix availability is separate from open source

**D:** [Official homepage](https://fonix.one/) says firmware **will** be free to download, with paid premium unlocking; [features](https://fonix.one/features) likewise describes future public availability. No downloadable firmware, source repository or source reuse license was found in the inspected official pages. This is a bounded finding, not proof that no private/beta build exists. A free binary would not itself grant modification or redistribution rights.

**D/U:** [Official specifications](https://fonix.one/specs) claim original WROOM-32, no PSRAM, AAC/M4A, SD and Bluetooth output. These are vendor claims, not independent measurements or reusable source evidence. Its advertised capacitive touch also does not establish compatibility with the user's unconfirmed CYD revision. Treat Fonix as the product reference, not the implementation base.

## AAC feasibility gate: required before committing to a base

1. **Identify the container.** `codec_name=aac`, `profile=LC`, `sample_rate=44100`, `channels=2` do not identify ADTS versus M4A/MP4. Helix's ADTS/ADIF/raw decoder is not an MP4 demuxer. Test the user's actual file/container; do not replace AAC with MP3 or assume renaming works.
2. **Prefer LC-only allocation.** Current codec-helix [source](https://raw.githubusercontent.com/pschatzmann/codec-helix/main/src/libhelix-aac/aaccommon.h) gates SBR on `HELIX_FEATURE_AUDIO_CODEC_AAC_SBR`; omit it for the LC experiment and verify the chosen release/build flags. This is a current-source observation, not proof of identical behavior in v0.9.4. Allocate only one active decoder.
3. **Budget real peaks, not total advertised SRAM.** Garion's [upstream stage-0 measurements](https://github.com/Garionhk/CYD-MP3-Player/blob/main/docs/stage0_results.md) report ~81-KB Bluetooth, ~32.5-KB MP3 decoder and transient connection costs. Replacing MP3 with LC AAC could fit (I), but AAC state, input/output buffers, task stacks, SD handles, pairing peaks and UI must all be measured. No inspected source proves the full required pipeline fits. The [current engine](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/app/audio.cpp) allocates `2048 × 2 × sizeof(int16_t)` = **8 KiB** PCM ring; its comment says 16 KB, so do not copy that comment into a memory budget.
4. **M4A fallback has limits.** AudioTools [ContainerM4A](https://raw.githubusercontent.com/pschatzmann/arduino-audio-tools/main/src/AudioTools/AudioCodecs/ContainerM4A.h) is audio-only/single-track and requires `moov` before `mdat`; sample-size tables can add memory. General M4A, large files and seek/resume require separate validation. Espressif's simple decoder is the alternative parser to evaluate.
5. **Pass condition (U):** sustained real-time SD AAC-LC stereo/44.1-kHz playback to **AirPods Pro 2**, including pairing/reconnect, pause/next and display interaction, with measured minimum internal heap, largest free block, stack high-water marks and underruns. Start with Wi-Fi disabled. Add the full UI only after audio passes. Repeat the required AAC playback through selectable external I2S output.

### AirPods Pro 2 and external DAC output

**D:** [Apple documents pairing AirPods Pro 2 with non-Apple Bluetooth devices](https://support.apple.com/en-gb/guide/airpods/dev499c9718b/web). This does not establish compatibility with a particular ESP32 build. **I/U:** start with AAC file decoding to PCM and standard **SBC A2DP transport**, then test the actual AirPods; do not interpret mandatory file AAC as mandatory Bluetooth AAC transport. Persist the selected address and test reconnection, volume/AVRCP behavior and earbuds returning from the case.

**I/U:** share the AAC decoder and route PCM to either A2DP or `I2SStream`; stop/drain the old output before switching and avoid allocating both output pipelines unnecessarily. AudioTools supports this composition and is consequently the stronger assembly fallback once selectable I2S is included; its [external DAC guide](https://github.com/pschatzmann/arduino-audio-tools/wiki/External-DAC) documents `I2SStream` transmission and configurable pins. Garion's shell remains valuable but its Bluetooth-specific engine needs an output abstraction. Use an external stereo DAC for line output and an appropriate headphone amplifier for direct headphone drive; a speaker power amplifier is not interchangeable with line/headphone output. Confirm accessible, output-capable GPIOs against this CYD's schematic before choosing BCLK/LRCLK/DOUT; the existing TFT/SD/touch pin use makes arbitrary example pin maps unsafe. No specific DAC, pin allocation or output switching implementation has been validated here.

## Minimal upstream starting points and version risks

- **Transport isolation:** [ESP32-A2DP `bt_music_sender.ino`](https://raw.githubusercontent.com/pschatzmann/ESP32-A2DP/main/examples/bt_music_sender/bt_music_sender.ino) is a small tone sender using frame callbacks. It is **GPLv3-or-later despite the library's Apache license**. It verifies transport only, not AAC.
- **AAC SD experiment:** [current `player-sdfat-a2dp.ino`](https://raw.githubusercontent.com/pschatzmann/arduino-audio-tools/main/examples/examples-communication/a2dp/player-sdfat-a2dp/player-sdfat-a2dp.ino) supplies the minimal SD→decoder→A2DP shape. Its shipped decoder is MP3: adapting to [`CodecAACHelix.h`](https://raw.githubusercontent.com/pschatzmann/arduino-audio-tools/main/src/AudioTools/AudioCodecs/CodecAACHelix.h), AAC file selection and correct container handling is an **untested adaptation**, not a ready-made AAC example. Keep its `TX_MODE` and silence-on-no-data behavior.
- **CYD hardware and shell:** Garion's [build script](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/tools/build_all.sh) names `stage0/s01_display_touch_sd`, `s02_bt_tone`, `s03_mp3_sd_bt`, then `app`. These are progressively useful upstream baselines; the MP3 stage is not the acceptance milestone. The script is compile-only and defaults to `min_spiffs`; its Bash tooling needs an existing compatible environment on Windows.
- **Documented shell versions:** Garion README specifies Arduino-ESP32 **3.3.10**, [ESP32-A2DP **v1.8.11**](https://raw.githubusercontent.com/pschatzmann/ESP32-A2DP/v1.8.11/library.properties), [libhelix **v0.9.4**](https://raw.githubusercontent.com/pschatzmann/arduino-libhelix/v0.9.4/library.properties). These are upstream-tested claims, not a build reproduced here. Pin a complete project snapshot and TFT_eSPI version too. Do not silently substitute current codec-helix for the old tag.
- **API coupling:** Garion's [decisions](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/docs/decisions.md) record subclass access to four protected A2DP members and callback overrides; upgrades need review. The same notes record failure of simultaneous Wi-Fi/BT on this board and justify separate images. [Build/partition documentation](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/flash.md) must match the selected snapshot; [published v1.1.1 release](https://github.com/Garionhk/CYD-MP3-Player/releases) is older than October entries on `main`.

## Remaining risks and research limits

The [board source](https://raw.githubusercontent.com/Garionhk/CYD-MP3-Player/main/app/board.h) assigns TFT to HSPI, SD to VSPI and touch to software SPI; reuse this deliberately rather than combining conflicting pin examples. The actual display controller, touch type and flash capacity still need identification. Whole-project reuse saves considerable UI/pairing work, but mandatory AAC, container support, bounded buffering and codec-independent seeking remain implementation work.

Licenses must be inventoried per copied file and pinned dependency: an Apache project shell does not remove GPL or Helix obligations. Missing-license projects are not automatic reuse candidates. Codec copyright permissions and any applicable AAC patent rights are separate; no legal clearance is asserted here. A personal experiment and redistribution have different obligations.

Validation performed: primary README/license/source/build-script inspection and cross-check of transport role, documented versions and memory claims. Several deeper GitHub paths were unavailable through retrieval; no exhaustive license audit, compile or hardware proof was possible within this research-only task. The research deliverable is complete; the **AAC hardware feasibility result remains open**.
